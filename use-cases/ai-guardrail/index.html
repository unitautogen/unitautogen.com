Available for PostgreSQL

A guardrail for
AI-written database code.

AI assistants now write a lot of database logic, and they write it fast. That is exactly where a silent mistake costs the most, and where it is hardest to catch by eye.

See the engine Download

The mistake no code review catches

Ask an AI editor to adjust a tier boundary and it might quietly change >= 1000 to > 1000. The edit reads fine, so it ships, and a customer with exactly 1000 points silently drops a tier. UnitAutogen already captured how that function behaved when it was correct, as committed pgTAP tests, so the change fails one of them before it reaches production.

Hand the whole loop to the assistant

Tell your assistant once to use UnitAutogen as its guardrail, then keep asking for features. On every change it runs the committed tests first, fixes what breaks that you did not ask to change, and regenerates only when the behaviour change was intended. Wired into CI, it checks AI-authored changes as fast as they are produced, so you keep the speed without shipping broken database logic.

See how it works

Set it once

Put one rule in your project's rules file - CLAUDE.md, AGENTS.md, or .cursor/rules - and the assistant follows it on every request:

Use UnitAutogen as the guardrail for all database work.
Whenever you add or change a function, procedure, trigger or RLS policy:
1. Run the committed guardrail tests first.
2. If a test fails and I did NOT ask for that behaviour to change, the
   code is wrong. Fix the code and re-run. Never edit a test to pass.
3. If this is new logic, or I confirmed the change was intended,
   regenerate the tests, run them, and commit them with the migration.
4. Tell me which tests ran, the pass/fail count, and what you regenerated.

Then just build (a real session)

You type plain feature requests. The assistant runs the guardrail loop each time and reports back. You never run a command.

You:

Add a membership_tier(p_points int) function that returns the tier: bronze under 500, silver from 500 to 999, gold 1000 and up.

Assistant: Added membership_tier and generated 6 guardrail tests covering the bronze, silver and gold boundaries. All 6 pass. I committed the tests next to the migration.

You, a week later:

Add a platinum tier for 5000 points and up.

Following the rule, the assistant runs the committed tests first, before it reports back. One fails:

not ok 4 - membership_tier :: p_points = 1000
    #   have: silver
    #   want: gold

Assistant: While adding platinum I had shifted the gold boundary to > 1000 instead of >= 1000, and the committed test for exactly 1000 points caught it (have: silver, want: gold). I corrected the check to >= 1000, confirmed all existing tests pass again, then regenerated to add coverage for the platinum tier. 8 tests, all green, committed.

You (this time you mean it):

Rename the bronze tier to "starter".

Now a failing test is the correct outcome. The assistant runs the committed tests, sees them fail with have: starter, want: bronze, recognises this is the rename you asked for, so it regenerates to re-pin the new behaviour instead of "fixing" the code, runs the fresh suite green, and commits.

The regression never left your machine, and you never ran a test. A failure you did not ask for means fix the code; a failure that matches what you asked for means re-pin the baseline, and the assistant makes that one judgement call from your instruction.
